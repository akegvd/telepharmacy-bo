## Project Conventions

- Node.js version is pinned to `24.19.0` (see `.nvmrc` and the `engines` field in `package.json`).
- Commit messages must follow [Conventional Commits](https://www.conventionalcommits.org/) (`<type>(<scope>): <subject>`), enforced by commitlint via a Husky `commit-msg` hook. Config: `commitlint.config.js`.
- Tests use Jest + React Testing Library (`jest.config.ts`, configured via `next/jest`). Test files sit directly beside the file they cover as `Component.test.tsx` / `useThing.test.ts` (same placement as `.stories.tsx`) — no `__tests__` subfolder. `npm run lint` and `npm test` both run on `git push` via the Husky `pre-push` hook. Every component and hook has a test — keep that up when adding new ones. Components using `next/navigation` mock it with `jest.mock`; components using TanStack Query wrap in a fresh `QueryClientProvider` and mock `shared/services/api/tasks`, not `fetch`.
- Component stories live next to the component as `Component.stories.tsx`, using `@storybook/nextjs-vite`. `.storybook/preview.tsx` wraps every story in the app's real MUI theme (`AppThemeProvider`) and sets `parameters.nextjs.appDirectory: true` globally — don't re-wrap or repeat that per story. Every component has a story; TanStack Query-backed ones (`TaskDetailContent`, `Dashboard`) seed the cache via the `withQueryClient` decorator (`shared/mocks/storyQueryClient.tsx`) instead of hitting a real API. Shared test fixtures live in `modules/dashboard/mocks/taskFixtures.ts` (`makeTask`) — reuse it rather than redefining task fixtures per file.
- Code under `src/` follows the domain-driven layout defined in [`PROJECT_STRUCTURE.md`](./PROJECT_STRUCTURE.md) — `src/app` holds routes only (delegating to modules), business/domain code lives in `src/modules/[domain]/{components,hooks,services,types,utils}`, generic non-domain code lives in `src/shared/`, and the MUI theme lives in `src/theme/`. Read that file before adding or reorganizing files.
- **DTO transform naming.** A `transformXxx` function's return type is a dedicated interface named `ITransform` + the function name capitalized (e.g. `transformTask` → `ITransformTask`, `transformTasksResponse` → `ITransformTasksResponse`), defined in its own file at `types/utils/transforms/<transformFileName>.ts` — module-owned transforms live under `modules/[domain]/types/utils/transforms/`, cross-module ones under `shared/types/utils/transforms/`. The transform implementation itself stays in the sibling `utils/transforms/<name>.ts`.
- **`display`-prefixed fields.** On a transform's output type, a field consumed only for rendering (passed to a component prop or interpolated into UI text) is named `displayXxx`; a field consumed only for logic (conditionals, filtering, equality checks, lookups keyed by it) keeps its plain name. A field used for **both** gets **both** keys — e.g. `status` (for `NEXT_STATUS[task.status]`, filtering) and `displayStatus` (for `<StatusChip status={task.displayStatus} />`) — even when they hold the identical value, because the prefix documents *how* a call site is using the field, not just what it contains. Don't collapse them into one key. See `modules/dashboard/types/utils/transforms/transformTask.ts` for a worked example.
- **Interface/type prefixes.** Every custom `interface` is prefixed `I` (e.g. `ITransformTask`, `INavItem`, `IErrorProps`); every custom `type` alias is prefixed `T` (e.g. `TStatus`, `TServiceType`, `TDataIssue`). Applies repo-wide, not just to transform DTOs. Exception: `declare module` augmentations of third-party types (e.g. `src/theme/palette.d.ts` extending MUI's `PaletteColor`) keep the upstream name as-is since renaming would break the augmentation.
